## Рабочая папка
Это папка на вашем компьютере, где лежат все файлы проекта — те, что вы сейчас редактируете, добавляете новые или удаляете. Пока вы не сделали для файлов специальную подготовку, они не «видны» системе контроля версий (Git). Например, если вы создали файл `main.py`, он сначала лежит только здесь — в рабочей папке. 
## Индекс (промежуточная область, staging area)
Это как «корзина перед оплатой». Вы явно переносите из рабочей папки в индекс те изменения, которые хотите зафиксировать в следующем коммите. Технически индекс — это специальный файл (часто `.git/index`), где Git сохраняет «снимок» того, что вы решили включить в коммит. Пока вы не выполнили `git add`, изменения из рабочей папки в индекс не попадут — и коммит их «не увидит». С помощью индекса можно собрать логичный коммит из изменений в нескольких файлах или отложить какие-то правки «на потом».

## Коммит
Коммит — это финальная фиксация: вы берёте всё, что лежит в индексе, и сохраняете как единое целое в истории проекта. Сам коммит — это «снимок» состояния всех файлов проекта в этот момент. Помимо этого «снимка», коммит хранит:
*   сообщение (описание, что и зачем изменилось);
*   имя автора и дату;
*   ссылку на предыдущий коммит (так формируется цепочка).

У каждого коммита есть уникальный идентификатор (хеш) — по нему в будущем можно точно вернуться к этому состоянию проекта. После создания коммита индекс обычно очищают: вы снова можете положить в него новую порцию правок для следующего коммита. 

## Как это работает на практике (для первого коммита)
Допустим, вы написали код в `main.py`. Сначала вы делаете `git add main.py` — файл попадает в индекс. И только потом `git commit -m "Первый коммит"` создаёт точку сохранения: берёт снимок из индекса, добавляет метаданные (автор, дата) и формирует коммит. Если после этого в рабочей папке остались ещё изменённые, но не добавленные в индекс файлы — они не войдут в этот коммит и останутся там. 

Так что цепочка такая: вы работаете в папке → явно переносите нужные изменения в индекс (`git add`) → фиксируете индекс в коммите (`git commit`). 
# Различия git diff и git diff --staged

## Что сравнивают эти команды

Обе команды используют `git diff`, но с разными парами состояний репозитория:

*   **`git diff`** сравнивает **рабочую директорию** (ваши файлы на диске) и **индекс** (staging area — промежуточное хранилище подготовленных к коммиту файлов). Она показывает изменения, которые вы внесли в файлы, но ещё не добавили в индекс с помощью `git add`.
*   **`git diff --staged`** (или `git diff --cached`) сравнивает **индекс** (то, что уже подготовлено к коммиту) и **последний коммит** (HEAD). Она показывает изменения, которые **уже добавлены в индекс** и будут включены в следующий коммит. 

## Жизненный цикл файла в Git

Чтобы лучше понять разницу, представьте жизненный цикл файла:
1.  **Рабочая директория:** вы редактируете файл (изменяете, добавляете новый).
2.  **Индекс (staging area):** вы выполняете `git add <файл>`, и файл переходит в состояние подготовленности (staged).
3.  **Последний коммит:** когда вы делаете `git commit`, содержимое индекса сохраняется как новый коммит в репозитории.

## Использованные команды

*   **`git status`** — показывает текущее состояние репозитория. Она отвечает на вопросы:
    *   Какие файлы уже добавлены в индекс (подготовлены к коммиту, состояние *staged*)? 
    *   Какие файлы изменены в рабочей директории, но ещё не проиндексированы (состояние *modified*, *changes not staged for commit*)? 
    *   Какие новые файлы появились в проекте и Git о них не знает (состояние *untracked*)? 
    *   На какой ветке вы сейчас находитесь.

    Вывод команды помогает понять, что именно готово к коммиту, а что нужно подготовить или отменить. 
*   **`git diff`** — демонстрирует различия между рабочим каталогом (файлами, которые вы редактируете) и индексом (staging area). То есть показывает изменения, которые **ещё не были добавлены** в индекс через `git add`. Это «неподготовленные» правки. 
*   **`git diff --staged`** (или эквивалентно `git diff --cached`) — сравнивает индекс (подготовленные к коммиту изменения) с последним коммитом (HEAD). Эта команда позволяет увидеть, **что именно войдёт в следующий коммит**. Если вы уже выполнили `git add`, но не сделали коммит, эта команда покажет проиндексированные изменения. 

## Как это работает вместе

Обычно эти команды используют в связке. Сначала `git status` даёт общую картину, а затем `git diff` (или `git diff --staged`) разбирает детали — показывает конкретные добавленные или удалённые строки.

## Важный нюанс

Если вы уже проиндексировали изменения через `git add`, то обычная команда `git diff` без флага `--cached` ничего не выведет, потому что она смотрит только на разницу между рабочим каталогом и индексом. Для просмотра проиндексированных изменений обязательно используйте `--staged`.
## Дополнительные возможности

Для `git diff` можно указывать конкретные файлы или хеши коммитов в качестве аргументов, чтобы сравнивать изменения в отдельных файлах или между конкретными коммитами. Также существуют полезные флаги, например, `--color-words` для подсветки изменённых слов.


# Различия между Git и GitHub

## Git
* **Что это.** Распределённая система контроля версий.
* **Основная задача.** Отслеживать изменения в файлах проекта, сохранять историю версий и позволять возвращаться к предыдущим состояниям.
* **Как работает.** При каждом коммите Git «фотографирует» состояние всех отслеживаемых файлов и сохраняет ссылку на этот снимок. Если файл не менялся, система не дублирует его, а ссылается на уже сохранённую идентичную версию.
* **Где работает.** Локально на компьютере разработчика. Не требует постоянного подключения к интернету.
* **Управление.** Через командную строку (терминал). 
* **Ключевые команды.** `git add` (добавляет изменения в индекс), `git commit` (создаёт коммит), `git status`, `git log` (просмотр истории), `git branch`, `git merge` (работа с ветками). 

## GitHub
* **Что это.** Онлайн-платформа для хостинга Git-репозиториев и организации совместной работы.
* **Основная задача.** Предоставлять облачное хранилище для проектов и инструменты для командной работы.
* **Как работает.** Автоматически синхронизирует репозитории (локальные копии на компьютерах разработчиков с облачным хранилищем).
* **Где работает.** Требует подключения к интернету.
* **Управление.** Через веб-интерфейс.
* **Ключевые функции.** 
  * **Репозитории.** Хранилище проектов (публичные доступны всем, частные — только определённым пользователям). 
  * **Форк (fork).** Создание копии чужого репозитория в своём аккаунте для самостоятельной работы. 
  * **Пулл-реквест (pull request).** Механизм предложения изменений в проект: вы вносите правки в своей копии, а затем предлагаете их «влить» в оригинальный проект.
  * **Код-ревью (code review).** Обсуждение правок с другими разработчиками.
  * **Иллюстрированные задачи (issues).** Система для отслеживания ошибок и предложений.
  * **GitHub Actions.** Автоматизация: настройка проверок (сборка, тесты, форматирование) и действий (развёртывание) при событиях в репозитории.
  * **GitHub Pages.**
## Важные нюансы
* **Git и GitHub не взаимозаменяемы.** Git — это базовый инструмент, а GitHub — сервис, построенный на его основе. Можно работать с Git локально, не используя GitHub. 
* **Git можно установить самостоятельно.** Вы можете настроить систему контроля версий на своём сервере или компьютере без обращения к сторонним облачным платформам.
* **GitHub популярен в опенсорс-сообществе.** Платформа удобна для вклада в открытые проекты, создания портфолио и демонстрации навыков. 
## Вывод
Если коротко: **Git** — это «движок», который следит за историей вашего кода, а **GitHub** — это «офис», который позволяет легко делиться проектом с командой и автоматизировать рутину.)

## Ветки

**Ветка** в Git — это независимая линия разработки. По сути, это указатель (ссылка) на конкретный коммит в истории проекта. Когда вы создаёте ветку, Git не копирует файлы — он просто создаёт новый указатель, который изначально ссылается на тот коммит, на котором вы находились при выполнении `git switch -c`.

**Что происходит при новом коммите?** Когда вы делаете коммит в ветке, указатель этой ветки автоматически перемещается вперёд — он начинает ссылаться на новый коммит. Таким образом, каждый коммит «прикреплён» к конкретной ветке. Другие ветки при этом не затрагиваются.

**Что делает слияние?** Слияние (команда `git merge`) объединяет изменения из одной ветки в другую. Если вы сливаете ветку `explain-branches` обратно в `main`, Git находит общий предок (коммит, на который указывала `main` до начала работы над этой задачей) и создаёт новый коммит — **merge-коммит**. У этого коммита два родителя: последний коммит из `main` и последний коммит из `explain-branches`.

**Важный нюанс с `--no-ff`.** Без этого флага Git попытался бы выполнить **fast-forward merge**. Это значит, что он просто передвинул бы указатель `main` вперёд, напрямую следуя за веткой `explain-branches`. В результате в истории `main` не останется следа от того, что вы работали в отдельной ветке — линия `explain-branches` исчезнет. Флаг `--no-ff` запрещает fast-forward и заставляет Git создать отдельный merge-коммит, сохраняя историю обеих веток. Именно этот merge-коммит и ожидает увидеть сервис, поэтому его наличие подтверждает, что слияние прошло корректно.
