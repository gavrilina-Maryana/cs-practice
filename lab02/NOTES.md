## Рабочая папка
Это папка на вашем компьютере, где лежат все файлы проекта — те, что вы сейчас редактируете, добавляете новые или удаляете. Пока вы не сделали для файлов специальную подготовку, они не «видны» системе контроля версий (Git). Например, если вы создали файл `main.py`, он сначала лежит только здесь — в рабочей папке. 
## Индекс (промежуточная область, staging area)
Это как «корзина перед оплатой». Вы явно переносите из рабочей папки в индекс те изменения, которые хотите зафиксировать в следующем коммите. Технически индекс — это специальный файл (часто `.git/index`), где Git сохраняет «снимок» того, что вы решили включить в коммит. Пока вы не выполнили `git add`, изменения из рабочей папки в индекс не попадут — и коммит их «не увидит». С помощью индекса можно собрать логичный коммит из изменений в нескольких файлах или отложить какие-то правки «на потом».

## Коммит
Коммит — это финальная фиксация: вы берёте всё, что лежит в индексе, и сохраняете как единое целое в истории проекта. Сам коммит — это «снимок» состояния всех файлов проекта в этот момент. Помимо этого «снимка», коммит хранит:
*   сообщение (описание, что и зачем изменилось);
*   имя автора и дату;
*   ссылку на предыдущий коммит (так формируется цепочка).

У каждого коммита есть уникальный идентификатор (хеш) — по нему в будущем можно точно вернуться к этому состоянию проекта. После создания коммита индекс обычно очищают: вы снова можете положить в него новую порцию правок для следующего коммита. 

## Как это работает на практике (для первого коммита)
Допустим, вы написали код в `main.py`. Сначала вы делаете `git add main.py` — файл попадает в индекс. И только потом `git commit -m "Первый коммит"` создаёт точку сохранения: берёт снимок из индекса, добавляет метаданные (автор, дата) и формирует коммит. Если после этого в рабочей папке остались ещё изменённые, но не добавленные в индекс файлы — они не войдут в этот коммит и останутся там. 

Так что цепочка такая: вы работаете в папке → явно переносите нужные изменения в индекс (`git add`) → фиксируете индекс в коммите (`git commit`). 
# Различия git diff и git diff --staged

## Что сравнивают эти команды

Обе команды используют `git diff`, но с разными парами состояний репозитория:

*   **`git diff`** сравнивает **рабочую директорию** (ваши файлы на диске) и **индекс** (staging area — промежуточное хранилище подготовленных к коммиту файлов). Она показывает изменения, которые вы внесли в файлы, но ещё не добавили в индекс с помощью `git add`.
*   **`git diff --staged`** (или `git diff --cached`) сравнивает **индекс** (то, что уже подготовлено к коммиту) и **последний коммит** (HEAD). Она показывает изменения, которые **уже добавлены в индекс** и будут включены в следующий коммит. 

## Жизненный цикл файла в Git

Чтобы лучше понять разницу, представьте жизненный цикл файла:
1.  **Рабочая директория:** вы редактируете файл (изменяете, добавляете новый).
2.  **Индекс (staging area):** вы выполняете `git add <файл>`, и файл переходит в состояние подготовленности (staged).
3.  **Последний коммит:** когда вы делаете `git commit`, содержимое индекса сохраняется как новый коммит в репозитории.
