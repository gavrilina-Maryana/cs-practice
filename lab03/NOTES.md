## Рабочая папка
Это папка на вашем компьютере, где лежат все файлы проекта — те, что вы сейчас редактируете, добавляете новые или удаляете. Пока вы не сделали для файлов специальную подготовку, они не «видны» системе контроля версий (Git). Например, если вы создали файл `main.py`, он сначала лежит только здесь — в рабочей папке. 
## Индекс (промежуточная область, staging area)
Это как «корзина перед оплатой». Вы явно переносите из рабочей папки в индекс те изменения, которые хотите зафиксировать в следующем коммите. Технически индекс — это специальный файл (часто `.git/index`), где Git сохраняет «снимок» того, что вы решили включить в коммит. Пока вы не выполнили `git add`, изменения из рабочей папки в индекс не попадут — и коммит их «не увидит». С помощью индекса можно собрать логичный коммит из изменений в нескольких файлах или отложить какие-то правки «на потом».

## Коммит
Коммит — это финальная фиксация: вы берёте всё, что лежит в индексе, и сохраняете как единое целое в истории проекта. Сам коммит — это «снимок» состояния всех файлов проекта в этот момент. Помимо этого «снимка», коммит хранит:
*   сообщение (описание, что и зачем изменилось);
*   имя автора и дату;
*   ссылку на предыдущий коммит (так формируется цепочка).

У каждого коммита есть уникальный идентификатор (хеш) — по нему в будущем можно точно вернуться к этому состоянию проекта. После создания коммита индекс обычно очищают: вы снова можете положить в него новую порцию правок для следующего коммита. 

## Как это работает на практике (для первого коммита)
Допустим, вы написали код в `main.py`. Сначала вы делаете `git add main.py` — файл попадает в индекс. И только потом `git commit -m "Первый коммит"` создаёт точку сохранения: берёт снимок из индекса, добавляет метаданные (автор, дата) и формирует коммит. Если после этого в рабочей папке остались ещё изменённые, но не добавленные в индекс файлы — они не войдут в этот коммит и останутся там. 

Так что цепочка такая: вы работаете в папке → явно переносите нужные изменения в индекс (`git add`) → фиксируете индекс в коммите (`git commit`). 


# Сравнение команд git diff, git show и git log

## Отличия команд

| Команда | Что показывает | Ключевая особенность |
|---|---|---|
| **`git diff`** | Различия между состояниями репозитория (например, рабочая директория vs индекс, два коммита). | Сравнивает **состояния**. По умолчанию — рабочую директорию и индекс (неиндексированные изменения). Можно сравнивать индекс с последним коммитом (`--cached`), два коммита или указывать конкретные хеши. |
| **`git show`** | Детальную информацию об **одном конкретном коммите**: метаданные (автор, дата, сообщение) и полный diff изменений. | Раскрывает **один коммит целиком**. Если указать хеш, покажет все внесённые в него правки. |
| **`git log`** | Историю коммитов в репозитории. | Выводит **список коммитов** с возможностью фильтрации и форматирования. Не показывает незафиксированные изменения (для этого есть `git status`). |

## Что именно нашли команды

*   **`git log --oneline --stat`**
    Эта команда вывела **сжатую историю коммитов** (каждый в одну строку благодаря `--oneline`) с дополнительной статистикой изменений для каждого коммита (`--stat`). Опция `--stat` показывает количество добавленных и удалённых строк в каждом изменённом файле. 

*   **`git diff HEAD~2 HEAD -- lab03/calc.py`**
    Команда **сравнила два коммита** (`HEAD~2` — коммит двумя шагами выше `HEAD` и `HEAD` — текущий коммит) и показала различия **только в файле `lab03/calc.py`**. Двойное тире (`--`) обязательно для указания пути к файлу. 

*   **`git show HEAD~1`**
    Команда **подробно показала коммит, который находится на один шаг выше `HEAD`**. Вывела его метаданные и полный diff изменений. 

*   **`git log -S"def" --oneline -- lab03/calc.py`**
    Опция `-S` (или `--find-same-as`) **ищет коммиты, в которых был изменён файл, и возвращает те, в сообщении которых встречается строка `def`**. Дополнительно используется `--oneline` для компактного вывода и `--lab03/calc.py`, чтобы ограничить поиск только этим файлом. 

*   **`git blame lab03/calc.py`**
    Команда **аннотировала каждую строку файла `lab03/calc.py` информацией о последнем коммите, который её изменил**: хешем коммита, автором и временной меткой. Это полезно, чтобы понять, кто и когда написал конкретную строку кода.

## Вывод

Таким образом, эти команды решают разные задачи:
*   **`git log`** — просмотр и поиск в истории коммитов.
*   **`git diff`** — сравнение состояний и просмотр изменений.
*   **`git show`** — детальный разбор одного коммита.
*   **`git blame`** — отслеживание авторства на уровне строк файла.
## Отличие `git revert` от `git reset --hard`

**Команда `git revert`** создаёт **новый коммит**, который отменяет изменения из указанного коммита. При этом исходный коммит **сохраняется** в истории. История остаётся линейной: `A → B → C`, после `git revert B` получается `A → B → C → D` (где `D` — коммит-отменатор).

**`git reset --hard`**, напротив, **переписывает историю**, перемещая указатель текущей ветки (HEAD) на выбранный коммит. Все коммиты после него **исчезают** из истории ветки.
## Почему в опубликованной истории безопаснее `git revert`

Это ключевое правило для командной работы. Если коммит уже был опубликован (вы сделали `git push`), то его изменение (переписывание истории) **нарушит работу других разработчиков**. Они могли уже склонировали ветку, работали с коммитом локально и теперь столкнутся с конфликтами при слиянии. 

С `git revert` всё прозрачно: участники команды видят в истории, что был сделан откат. Они могут легко понять причину и при необходимости создать свой коммит-отменатор.

С `git reset --hard` ситуация ещё хуже: после переписывания истории всем придётся делать `git push --force`, что повышает риск потери данных и создаёт путаницу. 

## Когда что применять

*   **`git revert`** — ваш выбор для **опубликованных** изменений, особенно в общих ветках (`main`, `develop`)
*   **`git reset --hard`** — допустим **только для локальных изменений**, которые вы ещё не отправляли другим.

## Важные нюансы

*   Для `git revert` рабочая директория должна быть чистой (без незакоммиченных изменений).
*   Если нужно отменить несколько коммитов одним общим коммитом, используйте `git revert --no-commit` (или `-n`). Она подготовит изменения локально, и вы сможете создать итоговый коммит вручную.
*   При отмене могут возникнуть **конфликты**, если код после исходного коммита сильно изменился.

## Разница между `git reset --hard` и `git revert`

Эти команды решают задачу отмены изменений, но работают принципиально по-разному. 

**`git reset --hard`**
* **Что делает:** Перемещает указатель `HEAD` на указанный коммит. При этом **очищает индекс** (staging area) и **перезаписыват рабочую директорию** содержимым этого коммита.
* **Последствия:** Все изменения, которые не были зафиксированы в коммите, **теряются безвозвратно**. Это деструктивная операция: если после `reset --hard` вы попытаетесь что-то запушить, Git выдаст ошибку, потому что история «разъехалась».
* **Когда использовать:** Только для **локальных изменений**, которые ещё не отправлены в общий репозиторий.

**`git revert`**
* **Что делает:** Создаёт **новый коммит**, который отменяет изменения указанного коммита. При этом **исходная история сохраняется** — коммиты не стираются, а добавляется линейная ветка с откатом.
* **Почему безопаснее для опубликованной истории:** Если коммит уже был отправлен другим разработчикам, использование `reset` **переписывает общую историю**. При следующем `pull` у коллег могут возникнуть конфликты: их локальная история «отстанет» от той, что пришла из удалённого репозитория. `revert` же добавляет явную «отметку отмены» в виде нового коммита — это позволяет всем участникам команды синхронизироваться без конфликтов.
## Важные нюансы
* Перед выполнением `git revert` рабочая директория должна быть чистой (без незакоммиченных изменений).
* При отмене могут возникнуть **конфликты слияния**, если после отменяемого коммита файл менялся ещё раз — их придётся разрешить вручную.
* Если нужно отменить сразу несколько коммитов одним коммитом, можно использовать `git revert` с диапазоном и флагом `--no-commit` (или `-n`): он подготовит отмены локально, но не создаст коммит сразу.

## Отличия тегов от веток в Git

| Критерий | Ветка (Branch) | Тег (Tag) |
|---|---|---|
| **Суть** | Подвижный указатель на линию разработки. Позволяет вести параллельную работу над разными функциями или исправлениями ошибок. | Неподвижная метка на конкретный коммит. Используется для обозначения значимых, стабильных точек в истории проекта, чаще всего — версий релизов. |
| **Поведение при новых коммитах** | Указатель ветки автоматически перемещается вперёд, на новый коммит. | Не изменяется после создания — всегда ссылается на один и тот же коммит. |
| **История** | Формирует иерархическую структуру — «дерево» с разветвлениями (когда одна ветка начинает отходить от другой). | Историю не хранит — это просто ссылка на снимок (сниппет) кода в определённый момент. |
| **Типы** | Не делится на типы. | Есть два типа: **лёгковесные** (lightweight) — просто указатель на коммит без метаданных, подходят для временных меток; **аннотированные** (annotated) — полноценные объекты с метаданными (автор, дата, сообщение, опциональная GPG-подпись). |
| **Когда использовать** | Для разработки, экспериментов, исправления ошибок. | Для маркировки стабильных состояний, релизов, передачи информации другим разработчикам. 

## Пример использования

*   **Ветка:** `feature/new-button` — создаётся для разработки новой кнопки, в ней делаются коммиты, затем она сливается с основной веткой (`main`/`master`).
*   **Тег:** `v1.0.0` — создаётся в момент релиза, чтобы другие разработчики могли легко перейти к этому конкретному, проверенному состоянию проекта. 
## Важные нюансы

*   По умолчанию `git push` не отправляет теги в удалённый репозиторий. Для этого нужно использовать флаг `--tags`. 
*   При переключении на тег (`git checkout <тег>`) репозиторий переходит в состояние отсоединённого `HEAD`, создавая новый коммит на основе помеченного коммита. Чтобы начать работу с кодом из тега, обычно сначала создают новую ветку от этого тега.


Такой формат хорошо структурирует информацию и сразу даёт чёткое понимание различий. Если нужно углубиться в детали (например, как именно работают аннотированные теги или как правильно сливать ветки), напишите — я дополню заметку!
