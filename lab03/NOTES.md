# Сравнение команд git diff, git show и git log

## Отличия команд

| Команда | Что показывает | Ключевая особенность |
|---|---|---|
| **`git diff`** | Различия между состояниями репозитория (например, рабочая директория vs индекс, два коммита). | Сравнивает **состояния**. По умолчанию — рабочую директорию и индекс (неиндексированные изменения). Можно сравнивать индекс с последним коммитом (`--cached`), два коммита или указывать конкретные хеши. |
| **`git show`** | Детальную информацию об **одном конкретном коммите**: метаданные (автор, дата, сообщение) и полный diff изменений. | Раскрывает **один коммит целиком**. Если указать хеш, покажет все внесённые в него правки. |
| **`git log`** | Историю коммитов в репозитории. | Выводит **список коммитов** с возможностью фильтрации и форматирования. Не показывает незафиксированные изменения (для этого есть `git status`). |

## Что именно нашли команды

*   **`git log --oneline --stat`**
    Эта команда вывела **сжатую историю коммитов** (каждый в одну строку благодаря `--oneline`) с дополнительной статистикой изменений для каждого коммита (`--stat`). Опция `--stat` показывает количество добавленных и удалённых строк в каждом изменённом файле. 

*   **`git diff HEAD~2 HEAD -- lab03/calc.py`**
    Команда **сравнила два коммита** (`HEAD~2` — коммит двумя шагами выше `HEAD` и `HEAD` — текущий коммит) и показала различия **только в файле `lab03/calc.py`**. Двойное тире (`--`) обязательно для указания пути к файлу. 

*   **`git show HEAD~1`**
    Команда **подробно показала коммит, который находится на один шаг выше `HEAD`**. Вывела его метаданные и полный diff изменений. 

*   **`git log -S"def" --oneline -- lab03/calc.py`**
    Опция `-S` (или `--find-same-as`) **ищет коммиты, в которых был изменён файл, и возвращает те, в сообщении которых встречается строка `def`**. Дополнительно используется `--oneline` для компактного вывода и `--lab03/calc.py`, чтобы ограничить поиск только этим файлом. 

*   **`git blame lab03/calc.py`**
    Команда **аннотировала каждую строку файла `lab03/calc.py` информацией о последнем коммите, который её изменил**: хешем коммита, автором и временной меткой. Это полезно, чтобы понять, кто и когда написал конкретную строку кода.

## Вывод

Таким образом, эти команды решают разные задачи:
*   **`git log`** — просмотр и поиск в истории коммитов.
*   **`git diff`** — сравнение состояний и просмотр изменений.
*   **`git show`** — детальный разбор одного коммита.
*   **`git blame`** — отслеживание авторства на уровне строк файла.
## Отличие `git revert` от `git reset --hard`

**Команда `git revert`** создаёт **новый коммит**, который отменяет изменения из указанного коммита. При этом исходный коммит **сохраняется** в истории. История остаётся линейной: `A → B → C`, после `git revert B` получается `A → B → C → D` (где `D` — коммит-отменатор).

**`git reset --hard`**, напротив, **переписывает историю**, перемещая указатель текущей ветки (HEAD) на выбранный коммит. Все коммиты после него **исчезают** из истории ветки.
## Почему в опубликованной истории безопаснее `git revert`

Это ключевое правило для командной работы. Если коммит уже был опубликован (вы сделали `git push`), то его изменение (переписывание истории) **нарушит работу других разработчиков**. Они могли уже склонировали ветку, работали с коммитом локально и теперь столкнутся с конфликтами при слиянии. 

С `git revert` всё прозрачно: участники команды видят в истории, что был сделан откат. Они могут легко понять причину и при необходимости создать свой коммит-отменатор.

С `git reset --hard` ситуация ещё хуже: после переписывания истории всем придётся делать `git push --force`, что повышает риск потери данных и создаёт путаницу. 

## Когда что применять

*   **`git revert`** — ваш выбор для **опубликованных** изменений, особенно в общих ветках (`main`, `develop`)
*   **`git reset --hard`** — допустим **только для локальных изменений**, которые вы ещё не отправляли другим.

## Важные нюансы

*   Для `git revert` рабочая директория должна быть чистой (без незакоммиченных изменений).
*   Если нужно отменить несколько коммитов одним общим коммитом, используйте `git revert --no-commit` (или `-n`). Она подготовит изменения локально, и вы сможете создать итоговый коммит вручную.
*   При отмене могут возникнуть **конфликты**, если код после исходного коммита сильно изменился.
